## Universal H700 image (§9.2)
One image, device chosen explicitly by `DEVICE=` in `NUUBOS_BOOT/nuubos.conf`. Selectors: rg-sp rg28xx rg34xx rg34xx-sp rg34xx-sp-v2 rg35xx-2024 rg35xx-2024-v6 rg35xx-h rg35xx-h-v6 rg35xx-plus rg35xx-plus-v6 rg35xx-pro rg35xx-sp rg35xx-sp-v2 rg40xx-h rg40xx-h-v2 rg40xx-v rg40xx-v-v2 rgcubexx. RG40XX-V V2 uses `rg40xx-v-v2` where the repo expects it; never silently substitute another board profile. Empty/invalid DEVICE must fail safely, never boot a random DTB. The file is read by U-Boot PREBOOT (patch 0001): `env import -t -r` (Windows CRLF lines), then two `setexpr DEVICE sub` with an empty replacement (`'^[^a-z0-9-]+' ''`, then `'[^a-z0-9-].*' ''`) keep only the first run of a-z/0-9/'-', so spaces, tabs, quotes and a trailing comment are dropped. No back-reference: old hush strips backslashes even inside single quotes (and again when it re-parses a line), `'\1'` and `'\\1'` both reached setexpr as `1` (2026-10-25, community report of a black screen on a CubeXX; the old `-t` kept the `\r` and the name matched nothing). Upper case is not folded (`RGCUBEXX` stays unsupported). Checked on the CubeXX 2026-10-25 with a debug build that dumped DEVICE/fdtfile to NUUBOS_BOOT: `DEVICE="rgcubexx"  # my cube` + CRLF -> `rgcubexx`, CubeXX DT. Not fail-closed in practice: an unmatched DEVICE leaves the invalid fdtfile, sysboot then boots with U-Boot's control DT (RG35XX Plus), a black screen on other panels (seen on the CubeXX; likely the community CubeXX black screen). After the test the CubeXX hit a kernel oops (undefined instruction, text lost; it had run minutes on the wrong DT and rebooted several times) and went back on the original bootloader for a while; SPL and TF-A are byte-identical, so the oops is probably unrelated. Final build flashed on the CubeXX the same day (normal `nuubos.cfg`, CubeXX DT); reaches consoles with the image or the OTA bootloader write.

## Family display/lid matrix (2026-10-11)
- Panels: 640x480 (RG35XX family, RG40XX-H/V, RG28XX), 720x480 (RG34XX, RG34XX-SP), 720x720 (RG CubeXX, 36 MHz = 60.0 Hz, a 120 Hz mode exists, the preferred 60 Hz one is used). Output scale (`nuubos-wl-output-apply panel_scale`): 1.125 for 720x720 and 720x480 (both ~255 ppi vs RG40XX-V ~200 ppi: 640x640 / 640x427 logical), else 1. ui-shot renders 720x480 too.
- RG28XX: its ST7701 panel is 480x640 mounted sideways. Device tree `rotation = <270>` (0020, as ROCKNIX) gives the connector "panel orientation" = Left Side Up; labwc never applied it: `package/nuubos/labwc/0004` sets `wlr_drm_connector_get_panel_orientation()` (transform 90) when a DRM output is enabled and draws its first-frame splash at the logical size; nuubos-splash reads the property and rotates the KMS and fbdev splash exactly as wlroots renders. Not hardware-qualified (no RG28XX on the bench); games are composited by labwc (no direct scan-out through a rotation).
- Clamshells (RG35XX-SP, RG34XX-SP, RG-SP and their v2 panels): gpio-keys `SW_LID` on PE7, wake source on lid open (upstream DT). nuubos-systemd owns the policy (system.md "Lid").
- RG28XX panel: upstream `panel-sitronix-st7701` (SPI, `anbernic,rg28xx-panel`), enabled in `linux.config` 2026-10-11; before that no driver matched and the screen stayed dark. No panel firmware blob needed.

## Family device mapping (2026-10-11)
Kernel patch `0103`, every board described as ROCKNIX does (`ROCKNIX/distribution`, `projects/ROCKNIX/devices/H700`). Hardware-qualified: RG40XX-V (also the V2 panel, `rg40xx-v-v2`, user 2026-10-16) and RG CubeXX (`0103` only adds the RTC to their DTBs, checked by decompiling before/after) and RG35XX Pro (input/rumble/LED qualified; its new PWM backlight is **untested**, no Pro screen on the bench). Every other board is **untested**.
- Face buttons: physical X (top) = PA2 = BTN_NORTH, Y (left) = PA3 = BTN_WEST on the whole family, fixed in the base `rg35xx-2024.dts` (mainline has them swapped; ROCKNIX keeps mainline and swaps back in its gamecontrollerdb / RetroArch "H700 Gamepad" configs, one config for every board).
- Sticks: two sticks on RG35XX-H, RG35XX Pro, RG34XX-SP, RG40XX-H, RG CubeXX; one on RG40XX-V; none on the others. Polarity: left X/Y inverted on all; right RX/RY inverted on RG34XX-SP, RG40XX-H, CubeXX (`dual-analog-inverted.dtsi`). RG35XX-H keeps the mainline `adc-joystick` node with ROCKNIX polarity (mainline had Y normal / RY inverted) and 4 ms polling (was 60 ms). L3/R3 on PE8/PE9 for every stick board (`thumb-buttons.dtsi` on RG34XX-SP and RG40XX-H, which lacked them).
- Rumble + sleep LED (user request 2026-10-11: the blinking power LED during sleep on every H700): the power LED of every board is PI12, which can be muxed to PWM2, so one coordinator (`drivers/input/misc/rg35xx-pro-haptics.c`, registers the `pwm-vibrator` FF input and `green:power`) owns rumble and LED everywhere; there is no generic `pwm-vibrator` node and no gpio-leds `led-0` any more (kernel `patches/linux/device/rg35xx-pro/0004`). `pwm2-rumble.dtsi` (base, motor on PWM2/PH2): `anbernic,rg35xx-pro-haptics` (sleep: PH2 gpio_in, PI12 on PWM2, 2.5 s period / 1.25 s on). `pwm3-rumble-pi13.dtsi` (RG40XX-H/V, CubeXX; UART5 on PH2/PH3 drives the RGB controller): deletes that node, `anbernic,rg40xx-v-power-led` owns the PWM2/PWM3 pair (shared pair clock; motor on PWM3/PI13, sleep LED 3 s / 1 s on). Works in deep sleep too (PWM clocks stay on). Hardware-confirmed on the CubeXX 2026-10-11 (deep); the RG35XX Pro and RG40XX-V keep their qualified behaviour; every other board untested. Deploy: `linux-rebuild`, copy `output/h700/images/*.dtb` to `/boot/`, reboot.
- Backlight: PWM0 on PD28, 0..100 (`pwm0-backlight.dtsi`) in the base. Before `0103` only RG40XX-V and CubeXX had it; every other board, RG35XX Pro included, had an on/off gpio-backlight (no brightness control).
- HDMI audio card on every board (included in the base).
- RTC: the Plus family (every board except the RG35XX 2024, both panels) has a battery-backed PCF8563-compatible RTC at r_i2c 0x51 (answering with a valid time on the CubeXX, 2026-10-11; ROCKNIX describes it on the whole family, mainline only on the SP). It is `rtc0` (`CONFIG_RTC_DRV_PCF8563=y`, built in so hctosys at boot reads it; the SoC `sun6i-rtc`, lost on power off, is `rtc1`). Its interrupt is not wired: no RTC alarm wake (nothing uses one). Verified on the CubeXX: hctosys from rtc0, `hwclock -w` writes it. To qualify: time kept across a cold power off without network.
- RGB on RG40XX-H: same MCU protocol and 16-LED layout as the CubeXX (ROCKNIX drives both with one frame, LEDs 0-7 right ring, 8-15 left), so `nuubos-rgb` reuses the CubeXX topology; the ROCKNIX `led-rgb` gpio-led on PI7 is removed so `nuubos-rgbd` can request PE5/PI7. Ring directions copied from the CubeXX, untested.

## Storage (§9.3)
SYSTEM (boot/root), STATE, USERDATA; SYSTEM/STATE never exposed as user storage. SD1 layout (MBR, `usr/lib/nuubos/partitions.sh`, 2026-10-12 for the A/B OTA slots, system.md): p1 system slot A (ext4 2 GiB, the flashed image), p2 NUUBOS_BOOT (vfat 16 MiB: `nuubos.cfg`, `nuubos-slot.cfg`), p3 STATE (ext4 128 MiB), p4 extended, p5 system slot B (2 GiB, empty until the first OTA), p6 USERDATA (exFAT, rest). The image holds p1-p3; S04 creates p4-p6 on the first boot (`sfdisk --append`, `partx --add`, PENDING token in STATE as before). The root is p1 or p5: scripts derive the disk from either (`nuubos_boot_disk`). Cards with the old layout (USERDATA = p4) are not migrated: reflash. A non-nuubOS-owned TF2 is never formatted automatically; formatting needs explicit user confirmation; migration/backup transactional and verifiable.

## SD card controller hang (2026-10-23, RG35XX Pro, kernel patch 0110)
- During the OTA download (payload written to /userdata, SanDisk SK128 11/2025, high speed 50 MHz) `sunxi-mmc 4020000.mmc: data error, sending stop command` at 477 s; the stop command went through, but the block layer's recovery command (CMD13) never raised an interrupt (hardware timeouts at their maximum, no software timeout in the driver): every later I/O to SD1 waited forever (hung tasks jbd2/mmcblk0p3, writeback), the console stayed alive but frozen (games did not start, SSH did not log in, the watchdog never fired). 400 MB over SSH to /dev/null or to /userdata did not trigger it; the real download did.
- Patch `0110-mmc-sunxi-reset-the-controller-on-a-request-timeout`: a delayed work armed with each request (5 s + 1 ms per KB of data, cancelled in finalize); on expiry it resets the controller (soft/FIFO/DMA + IDMAC), restores WIDTH, SD_NTSR and CLKCR, updates the clock and fails the request with -ETIMEDOUT so the MMC core recovers. Log line: "request timeout, cmd N, status ..., raw int ...: resetting the controller".
- How often (same Pro, same card, no battery, USB only): the full download with 0110 completed (`OK downloaded`, 79 s) with one data error (stop command failed too) recovered by the normal path, the watchdog not needed; the first boot of the nightly after the OTA logged 5 data errors between 8 and 15 s. Reading 1.5 GB of p1 and writing 1.5 GB to /userdata with Wi-Fi idle: 0 errors; 400 MB over SSH into /userdata (Wi-Fi RX + writes): 0. So errors come with SD writes/reads while Wi-Fi associates or runs HTTPS, not from the card alone. Candidates: Wi-Fi TX on the rails without a battery (SD vmmc = CLDO3), SDIO/SD interaction, the card. Next: the same download with the battery connected, and another card. No dynamic debug in the kernel: the error type (`sunxi_mmc_dump_errinfo` is dev_dbg) is not visible.
- Cause found (2026-10-23, same Pro, no battery): the power supply. With a fresh card (the old one no longer showed up in a PC reader) the first setup stalled as soon as Wi-Fi connected: STATE held a `wpa_supplicant.conf.tmp-*` never renamed, no user created (usersd's CREATE never reached the card; the same command works on the CubeXX), then a crash. With a stronger USB supply the setup completed and the first boot logged no SD error. Not a nuubOS issue (user decision): the Pro is rated 5 V 1.5 A (7.5 W) and was on a 5 V 1 A (5 W) supply; without a battery to cover them, the Wi-Fi TX peaks brought the SD down. Diagnosing a console with SSH off: copy STATE in a PC (`sudo cat /dev/mmcblk0p3 > file`), `e2fsck -fy` a copy to replay the journal, read it with `debugfs`.
- After such a hang the partial payload (`payload.part`) ends with data that never reached the card: the resumed download then fails with `ERR checksum` and starts over (correct, but the download is wasted). Since 2026-10-23 a part that was not stopped cleanly (no `payload.part.clean` with its size) loses its last 8 MiB before the resume instead.

## SD2 = games card (user decision 2026-10-11, replaces the v0.5 "USERDATA on TF2" model)
- SD1 is the console: SYSTEM, STATE and USERDATA (saves, states, BIOS, profiles, library, covers/metadata) stay there unless the user moves a category to SD2 ("Data on SD2" below, opt-in). SD2 is content (ROMs + media) and is used as it is: exFAT, FAT32 or ext4, partitioned or not (first supported partition). Removing SD2 never costs progress: its games become UNAVAILABLE (EPIC-011) and come back when it returns. The old SINGLE/AUTO/DUAL modes, the erase-and-adopt flow and the TF2→TF1 backup are gone (no migration: no adopted card existed).
- Hardware: kernel `0036` includes the TF2 slot (MMC2, CD PE22, supply PE4 always on, I/O cldo3, no 1.8 V) from the family base `rg35xx-2024.dts`, so every board has it; MMC aliases are fixed (TF2 = mmc2/mmcblk2). Wiring from Chris Morgan's upstream submission carried by ROCKNIX; tested on RG35XX Pro, RG40XX-V and RG CubeXX (user, 2026-10-11), every other board is untested.
- Lifecycle (`nuubos-storagectl`, udev `hotplug`, mount `/media/sd2`): none (no slot) / empty / checking / ready / readonly / unreadable / ejected / ignored. Insert → dirty check + repair → mount → libraryd `SCAN` → toast. Eject refuses with open files. Pulled out → lazy unmount, games unavailable, a running SD2 game is save-stated and closed (saves are on SD1). First time a card (CID, remembered in STATE) is seen: ROMs found → toast only; readable without ROMs → "Create Game Folders" / "Don't Use"; blank/unreadable → "Format SD2" / "Don't Use"; never over a game. "Don't Use" (user request 2026-10-11, instead of "Leave as is") really leaves the card alone: state `ignored`, unmounted, no library, no backup, no question when it comes back (CID in `/state/storage/sd2-ignored`); Storage shows "Not in use" + "Use SD2" (`sd2 use`), formatting it un-ignores it. Format only by explicit armed confirmation.
- ROM folders: `roms`, `ROMS`, `Roms` at the root (or system folders at the root, ArkOS) with per-system folder aliases in `systems.conf` (stock Anbernic/Onion, Knulli/Batocera/ROCKNIX, muOS). A game on both cards is one game (id = system + file name + size).
- Console backup (user request 2026-10-12: one backup of the console, no separate profile backup; the old `nuubos-backupctl` per-profile tar and its jobs are gone): `<volume>/nuubos-backup/<SID>/` (H700 chip id, survives an SD1 reformat), incremental, valid only once its manifest is written last, last 3 versions of changed files kept. Destination chosen by the user (System → Troubleshooting → Backup → Destination): SD2 (default where the board has a card slot), SD1 (`/userdata/nuubos-backup`, default without a slot; the row warns it is lost with SD1) or USB drive (first read-write volume under `/media`; nuubos-mediactl refreshes the status on connect/remove/eject and starts a due automatic backup on connect). Profiles and settings always included; selectable (all on by default): saves, save states, library, the user's screenshots & recordings, BIOS, covers & metadata (no scraped game screenshots since 2026-10-12). Never secrets (Wi-Fi keys, tokens, credentials, SSH keys). Automatic (default on): after a game session, daily, when the destination appears; never during a game. Restore (System → Troubleshooting → Recovery → Restore from Backup, and in the OOB when any backup is visible): every backup on SD2, SD1 and USB drives is listed (this console first), then "Entire Console" or one of its profiles. A profile restore replaces only that profile (`/state/users/<id>` keeping its secrets, and its `/userdata/users/<id>` profile, RetroArch app data, saves, states, screenshots/recordings, library); other profiles, device settings, BIOS, covers and the backup link are untouched. Restores are all or nothing (root cause of the 2026-10-12 report "no metadata after the restore": the old restore swapped area by area and stopped before its last area, covers & metadata, leaving a half-restored SD1 with no trace): every area is copied next to its live place (`<path>.restore-new`) and checked, then all are swapped; `/state/storage/restore.journal` lists them, `refresh` cleans up an interrupted copy or completes an interrupted swap (under `flock /run/nuubos/storage/backup.lock`, which backup and restore also hold). Log kept on SD1: `/userdata/logs/nuubos-backup.log` (rsync errors included, trimmed to 256 KB).
- Contract: `nuubos-storagectl` (status, `hotplug add|remove`, `sd2 attach|eject|ignore|use|prepare|format CID`, `data apply|move CAT sd2|sd1|forget CAT` writing `data.status` DATA_ON/STATE=none|online|offline|moving/MOVING/CONFLICTS, all serialised by `flock` on `/run/nuubos/storage/sd2.lock`; udev returns at once) writes `/run/nuubos/storage/sd2.status`; S05 writes `storage.status` (SD1) and starts `sd2 attach` in the background; `nuubos-sd2-backup` (the console backup; `refresh|set enabled|item|dest|reset|trigger|run|list|users DIR|restore DIR [USER]|archive`) writes `backup.status` and keeps its settings in `/state/storage/sd2-backup.conf`, its link token in `sd2-backup.state`, known cards in `sd2-known`. Each change pokes `nuubos-systemctl storage-changed` (never waits for the reply: systemd may be the one running the tool; it writes and closes at once, so nuubos-systemd reads a client's input before acting on its hang-up: until 2026-10-29 POLLHUP was checked first and every storage-changed was dropped unread, so Home saw card changes only with the next other snapshot). nuubos-systemd STATUS `storage.*` (`sd2.slot|state|cid|fs|label|prompt|total|free`, `backup.enabled|items|dest|available|found|last|result|card=none|linked|conflict|restorable`, card = the chosen destination's state); `data.on|state|moving|conflicts`; commands `STORAGE CHANGED`, `STORAGE SD2 EJECT|IGNORE|USE`, `STORAGE DATA FORGET cat` (systemctl `storage-data-forget`), `SET STORAGE BACKUP 0|1`, `SET STORAGE BACKUP_ITEM item 0|1`, `SET STORAGE BACKUP_DEST sd2|sd1|usb`, `STORAGE BACKUP ARCHIVE`. Jobs `storage-data-move CAT sd2|sd1`, `sd2-backup`, `sd2-backup-auto` (silent), `sd2-restore DIR [USER]`, `sd2-format CID`, `sd2-prepare`. A restore keeps the secrets of profiles already on SD1 and resets STATE permissions (700/600). The restore (Settings or OOB) runs on the full-screen operation screen (user request 2026-10-12, `op-hero` with `op-kind` 0 in home.slint, `storageui::start_restore`, shared with the system update): it owns the input, shows the job's progress (`nuubos-jobctl run --progress`) and a rotating light-hearted line (strings 997-1004, OOB greeting drum), "Keep the console on" (995); on success the central restart takes over; on failure Try Again (996) | Start from Scratch (964, OOB) / Close (239).
- Verified 2026-10-11 on the CubeXX with a loop exFAT image at /media/sd2 (no card in the bench slot): `Roms/` found, SD2-only game catalogued and made unavailable on removal (duplicate kept from SD1), full backup 1.2 GB in 1m37s, incremental 1.6 s, item off removes its copy, conflict refuses manual and automatic runs, restore 1m44s (settings back, RetroAchievements secret kept). Still to qualify with a real card: hotplug/CD, eject, dirty repair, format, the first-seen question, a game running from SD2 when it is pulled out, sleep with a card swap, the boards other than RG35XX Pro / RG40XX-V / CubeXX.
- Data on SD2 (GitHub #24, user decision 2026-10-29: muOS-style but opt-in, per category, nothing moves by default): Settings → System → Storage → Data on SD2 (page 75) lists BIOS (`bios`), Saves, Save States, Screenshots & Recordings (every profile's `users/<id>/saves|states|screenshots+recordings`) and Covers & Metadata (`library/covers|metadata|cache`, the scraping cache included), each SD1 or SD2. Profiles, settings, RetroArch app data and the library catalog always stay on SD1. A category on SD2 lives in `<card>/nuubOS/<same path>` and is bind-mounted over its `/userdata` folder by `nuubos-storagectl` (boot via S05 `data apply`, user switch, card attach/detach, after moves), so no service changes paths. `/userdata` is a shared mount and the active-user view `/run/nuubos/userdata` an rbind made rslave, so binds reach the view and its lazy unmount never reaches back; the TF1 view `/run/nuubos/storage/tf1` is private (never shows a bind): moves read and write SD1 through it.
  - One data card: `nuubOS/.nuubos-data` TOKEN = `/state/storage/data.conf` TOKEN; the first category moved claims the card, the next ones need that same card. Card out, ejected, ignored or another card: every folder of a category on SD2 is an empty read-only tmpfs (source `nuubos-sd2-data`), so nothing is written to SD1 meanwhile; emud refuses LAUNCH with `ERR data` (Home: "Insert the SD2 card with your data") while BIOS, saves or states are away or moving; Syncthing stops on the missing folder marker instead of syncing deletions. Eject and Don't Use release the binds first (open files → busy), so the card is really free. Format refuses the data card (`@error data`). A card gone for good: choosing SD1 offers "Use SD1" (`data forget`: back on the SD1 folders, which hold what was there before the move; the card keeps its copy).
  - Moves (job `storage-data-move CAT sd2|sd1`, progress on the row, refused while a game runs): the folders get the read-only placeholder, `/usr/lib/nuubos/nuubos-data-move` (nuubos-files) copies file by file into `.<name>.nuubos-move` next to the destination (space check first, 64 MB margin; SIGTERM = cancel, source untouched), commits by renames, removes each source file after its rename; a file already at the destination with the same bytes only goes from the source, a different one is a conflict: the destination's copy stays and the source's goes to `<destination root>/conflicts/<date>/<path>` (`/media/sd2/nuubOS/conflicts` or `/userdata/conflicts`), count shown after the move. An interrupted move is just run again. Profile deletion (usersd) unbinds first and deletes the profile's folder on the card too.
  - Console backup: an item on SD2 is skipped while the card is away (placeholders would empty the backup) and when the backup goes to SD2 itself; its old copy stays. A restore writes items on SD2 into the card's folders (card required, `fail card`); the restart after a restore rebuilds the binds.
  - Verified 2026-10-29 on the CubeXX with Screenshots & Recordings (12 files, both profiles): to SD2 and back by job and from the UI, md5 identical, binds visible in the user view, eject → read-only placeholders and the card fully released, Use SD2 → bound again; emud `ERR data` with saves away, not with screenshots only. Not yet tried on the device: the big categories (covers 2.2 GB), a real card pulled out with data on it, a conflict on the card (host test `nuubos-files/tests/data-move.py` covers it), restore with data on SD2.
- Proposed, not built (user question 2026-10-11): the same game under different file names on both cards is two games today; recognise identical content (same system and size, then CRC32 / sampled fingerprint) and link saves through a canonical name.

## Display (§22)
Initial brightness 60%; user brightness persists across reboot. Display state stays coherent across HDMI/internal panel changes: unrelated setting changes must not resurrect stale internal-panel brightness presentation while the panel is inactive.

## RGB (§27), battery/status (§28)
RGB depends on hardware capability: no controls for unsupported devices (rows show "Unavailable"); integrate with lifecycle/power. Battery/status is event-driven: AXP717 uses gauge events (`GAUGE_NEW_SOC`), not UI polling; keep that unless the driver/API requires otherwise.

## RGB Lighting redesign (user request 2026-10-08)
- `nuubos-rgbd` is only the hardware frame sink: persistent line protocol on `/run/nuubos/rgbd.sock` (`STATUS`, `FRAME` in LOGICAL order = zone by zone, position by position around the ring, mapped to physical LEDs through `led_indexes` in `rgb_common.c`, `OFF` = MCU + LED rail unpowered). No animation, brightness or policy there. `nuubos-rgbctl status|off|color R G B|locate N|frame ...` is a dev tool; `locate N` lights ring position N white and N+1 dim to qualify ring start/direction.
- `nuubos-lightingd` renders every frame (time-based, gamma 2.2, brightness 10..100 in steps of 10 as a perceptual gain; 30 fps timer only while something moves, nothing between events; MCU powered off when the ring is dark). Contract and event table in the header of `lightingd.c`; Home side in `nuubui-home/src/src/lighting.rs`.
- Effects (per user, `lighting.conf` FORMAT=2): Off, Solid, Breathing, Orbit, Aurora (default since 2026-10-11, user request: Aurora in the user's Mood accent, `COLOR=theme`; before Off; only users without a saved `lighting.conf` get it), Spectrum, Battery Level (gauge, charging LED pulses), Console Colors (colour of the running game's system from `systems.conf` field 6, via emud `SUBSCRIBE`; theme accent outside games). Colour = theme accent (read from the active user's theme, follows theme changes) or a fixed palette (same list in `lighting.rs` COLORS and `lighting-color-index()` in home.slint). Effect/colour dropdowns preview live on the LEDs (`Preview`/`EndPreview`, never persisted). Old v1 files (MODE/RED/GREEN/BLUE/SYSTEM_EFFECTS) are migrated on load. Without RGB hardware (`supported`=false) Settings → Controllers & Input has no RGB Lighting row and the section header is RUMBLE (string 899), also on the web page.
- Tasks layer (user request 2026-10-09): while a Live Notification runs (`progress=` in a POST/UPDATE; ended by a message for the same id without progress or DISMISS) and the user's tasks category is on, the ring shows the oldest one over the effect, under signals: accent gauge to the progress with a breathing head LED, or a slow accent comet when the progress is -1; crossfades in/out; frame timer runs while it is shown. The list is rebuilt from notifyd's replay at every (re)SUBSCRIBE. The completion still plays the tasks signal (fill/pulses).
- Media layer (user request 2026-10-14): lightingd SUBSCRIBEs to mediad (`state`, `position`, `duration`, extrapolated while playing); while music or a video plays/pauses and the per-user `MEDIA=1` (lighting.conf, default on; D-Bus `GetMediaProgress`/`SetMediaProgress`, set from the Media app) the ring is an accent gauge of the track position, the edge LED lit by its share, 45 % while paused; under tasks and signals. Screen off (`/run/nuubos/screen-off`, inotify on /run/nuubos) = ring dark and LED rail off except lifecycle shapes, unless the per-user `SCREEN_OFF=keep` (default `off`; D-Bus `GetScreenOffLighting`/`SetScreenOffLighting`, Media app Settings tab); the dark state wins over a running crossfade (the frame timer is stopped then); checked on the CubeXX (`backend=off`, 0 wakeups, back on with the screen). Not yet checked by eye: the gauge look on the real rings.
- System signals: five per-user categories (power, battery, connections, games, tasks), sourced from the EPIC-006 notification stream (`SUBSCRIBE` to notifyd: only POST starts a signal, Live Notifications only on completion) plus `Lifecycle(sleep|wake|shutdown)` from `lifecycle-lighting`. Grammar: one shape per meaning (link/unlink for connections, pulses for warning/error, fill for success/charging, spin for save/load state, flash for screenshots, tick for save slot, welcome/wake/farewell for power) and colour roles accent/success/warning/error/neutral. Enabling a category plays its signal. Priority: power > errors > warnings > info.
- Lifecycle is runtime-only (the 0.5 hook persisted brightness 0 during sleep): `sleep` fades and replies once dark, `wake` is ignored unless dark/darkening (systemd sends it at start-up and after a failed power off). `boot`, `restart`/`reboot`, `poweroff` (= legacy `shutdown`) are the LED side of the lifecycle splash animations, timed like them (ui.md "Lifecycle splash").
- Ring order (every topology in `rgb_common.c`; RG40XX-H reuses the CubeXX one, untested): position 0 = upper right LED, clockwise, 45 degrees apart, position 3 at the bottom (lightingd `RING_BOTTOM`). CubeXX qualified 2026-10-11: left ring `{15..8}`, right `{1, 0, 7..2}` (the two rings are wired in opposite directions). Diffused rings make neighbouring LEDs hard to tell apart: qualify with two LEDs 90 degrees apart in different colours (`nuubos-rgbctl frame` with position 0 white and position 2 red: expected at about 1:30 and 4:30), reported as clock positions, not with `locate`.

## Performance / power principles (§31)
H700 is constrained: optimize intentionally, not prematurely; keep proven hardware decisions unless new measurements justify change. Profiles Auto / Performance / Battery Saver are policy of the system service, never UI pages. Suspend/power changes need regression testing (Wi-Fi, Bluetooth, input wake, display, storage, audio interact). Never invent wake behavior beyond qualified hardware capability.
- CPU top OPP (2026-10-12): the H616 table's 1512 MHz point (speed bin 5 on the CubeXX: 1.16 V, the vdd-cpu maximum) corrupts memory under a sustained load (rsync of 440 MB: SIGILL/hung copies, "Bad page map" with stray high PTE bits, level 3 address size fault oopses; it broke the SD2 restore at the covers stage). Clean-boot runs of 10 copies: 1512 MHz 2 failed + 4 kernel errors; 1416, 1200, 1008 MHz 0/0. `patches/linux/h700/0105` deletes `opp-1512000000` in the family base (`rg35xx-2024.dts`): every H700 board tops out at 1416 MHz. Measured on the CubeXX only; RG40XX-V / RG35XX Pro to qualify. One hard freeze was seen once at ≤1416 MHz on battery during repeated stress (under investigation). Seen again 2026-10-14 on the CubeXX on 7.3-rc7: a reboot (panic=10 or watchdog, no log kept: no pstore) ~35 s into God of War PSP at 35 fps (CPU 1416 MHz, GPU 600 MHz, 61 °C), on battery (user had unplugged it); no failure in ~20 minutes of the same load on mains afterwards. Points at power delivery under peak load on battery (AXP717 rails), not at the code; ramoops cannot keep a log across the reset (see "No persistent kernel log"); a CPU lockup now panics and restarts.
- VDD-DRAM forced to 1.1 V on every board (found 2026-10-29, perf-power.md 1.1): the family DTS fixed `vdd-dram` (AXP717 DCDC3, reg 0x85, 0.5 V + n x 10 mV up to 1.2 V) with min = max = 1.1 V, so U-Boot proper (regulator uclass autoset) and Linux (apply_uV) overrode the SPL's boot0 voltage (DDR3 1.5, LPDDR3 1.2, LPDDR4 1.1 V). The CubeXX is LPDDR3 (RTC GP1 0x30fa = vendor LPDDR3 profile; JEDEC 1.14-1.30 V) and ran under-volted: the bit flips of the "1512 MHz OPP" and of the panfrost oopses. Fixed by kernel 0112 + U-Boot 0008 (range 1.1-1.5 V: the SPL's value stays). Check on a device: `i2cget -f -y 0 0x34 0x85` (0x46 = 1.20 V on LPDDR3) and `devmem 0x07000104 32` (para1 of the profile the SPL chose). The 1512 MHz OPP (0105) and the GPU 600 MHz verdicts were made on under-volted DRAM: requalify them before relying on them.
- Idle audit (2026-10-14, CubeXX, Home idle, screen on, Aurora lighting; `/proc/interrupts`, `/proc/stat` ctxt and per-thread `voluntary_ctxt_switches` deltas; same on 7.2.8 and 7.3-rc7): ~3600 context switches/s with the UI itself near zero. Sources: (1) `adc-joystick` input-poller at 4 ms (`poll-interval = <4>`, 0103), always open by inputd: 500 GPADC IRQ/s, ~1300 `events_freezable` kworker switches/s, plus the remote-wakeup IPIs; the poller `max` equals the DT value, so `/sys/class/input/inputN/poll` cannot be raised at runtime (EINVAL) without a kernel change. (2) schedutil ping-pong 1032↔1416 MHz, ~30 transitions/s, each 1416 step raising vdd-cpu over I2C (~120 `mv64xxx_i2c` IRQ/s); `rate_limit_us` 835 → 10000 cut transitions only to 25/s but quadrupled the time at 1416 MHz (3.6 % → 15 %): do not raise it. (3) RGB at 30 fps: rgbd ~180 + lightingd ~110 + 8250 kworkers ~120 switches/s, ttyS2 150 IRQ/s (rgbd `tcdrain()`s every frame). (4) SDIO Wi-Fi ~200 IRQ/s with power save on (`disable_lps_deep=Y` kept: proven firmware RPWM failure). CPU never runs below 1032 MHz: 480/720 MHz have the same 900 mV as 1032, so the Energy Model marks them inefficient and schedutil skips them (by design, not a bug). No cpuidle states then (v0.5 left them out without a recorded reason; TF-A `0001`/`0002` implement the CPU power-down state `0x00010000`). The analog sink never suspends (audio.md, anti-pop): 0 wakeups but codec bias stays On.
- Battery work done (user request 2026-10-14, "implement them all"; CubeXX, 7.3-rc7): (1) stick polling: kernel `0106` lets `/sys/class/input/inputN/poll` of `adc-joystick` go up to 100 ms, nuubos-inputd sets 4 ms while a game owns the controllers (`GAMEPADS ON`), 16 ms in menus, 100 ms while `/run/nuubos/screen-off` exists (inotify), only on `adc-joystick` devices (the RG35XX-H has another polled device); (2) screen off caps the CPU at 1032 MHz (power.sh `SCREEN_OFF_CPU_MAX`, `nuubos-power-mode refresh` called by `nuubos-displayctl screen on|off`): no 1032<->1416 ping-pong and no vdd-cpu I2C writes while dark; (3) lightingd: an effect alone draws Aurora/Spectrum/Battery at 15 fps, Breathe at 20, Orbit at 30; in Battery Saver (`/run/nuubos/battery-saver`, written by power.sh with the effective profile) at most 10 fps and half brightness (identical frames were already skipped); (4) audiod parks the speaker amplifier (codec `Speaker` DAPM pin) while the screen is off and nothing plays (audio.md); (5) kernel `0107`: CPU power-down idle state `cpu-sleep-0` (entry 100 us, exit 500 us, min residency 5 ms, `local-timer-stop`), qualified on the CubeXX with deep sleep/resume and heavy emulation (same fps); (6) `linux.config`: `NR_CPUS=4`, no `NUMA`, `HIBERNATION`, `AUDIT`, `VIRTUALIZATION` (Image -360 KB); (7) nuubui-home shares one system bus connection (ui.md). Measured idle in Home, screen on: context switches 3626 -> 1927/s, GPADC IRQs 500 -> 200/s, timer 1140 -> 480/s, IPIs ~900 -> 401/s, RGB UART 151 -> 76/s (50 in Battery Saver), cores powered down 78 % of the time; screen off: 767 context switches/s, 0 frequency transitions, cores down 92 %. Power itself could not be measured: the AXP717 `current_now` is a slow model value (a backlight change 10 -> 60 % did not move it over 20 s windows): judge by a battery run-down instead. Wi-Fi: power save on by default (off only for streaming/netplay) and Deep LPS under qualification (connectivity.md); before this, power save was off after the first sleep (`nuubos-suspend`).
- Kernel optimizations (user request 2026-10-14, "vai procedi"; CubeXX, 7.3-rc7), `linux.config`: (1) 3-level page tables, `ARM64_VA_BITS_39` + `PA_BITS_48` (was the arm64 defconfig's 52-bit/LPA2 with 5 levels folded to 4 at runtime: the A53 has no LPA2): shorter TLB-miss walks, smaller page tables, the 52-bit PTE encoding gone; user space gets 256 GiB of address space. (2) zram swap: `ZRAM` + lz4, `S07nuubos-zram` sets up 384 MiB on `/dev/zram0`, `swappiness` 100, `page-cluster` 0 (no disk swap anywhere). (3) MGLRU (`LRU_GEN`, enabled). (4) Lockup detectors: soft lockup (panic after 1 period, `BOOTPARAM_SOFTLOCKUP_PANIC=1`, an int since 7.3), hard lockup via the buddy detector (no pseudo-NMI on GICv2) with panic, hung task warnings (no panic): with `panic=10` a stuck CPU now restarts the console instead of freezing it (a whole-SoC hang with every CPU stuck still needs a power cycle). Qualified: quick regression 133 PASS / 0 WARN (the 11 FAILs are the stale H6/H8 tests, open-items.md), memory stress (own fill/verify tool, 2×300 MiB × 6 passes and 2×380 MiB × 4 passes with 280 MiB through zram: 0 errors, no OOM, no kernel message, UI alive), Home idle cores powered down 74-77 % (75.8 % before). Rejected: cpuidle TEO (cores down 32-36 % vs 74-77 % with menu, same idle Home). THP stays `always` (measured 2026-10-14, CubeXX on mains): God of War PSP from its automatic state, 40 s per run, always/madvise alternated twice: 23/22 and 22/23 fps (frameskip 2), AnonHugePages 350 vs 303-325 MiB, MemAvailable within run-to-run noise; with the UI restarted in each mode AnonHugePages ~147 MiB both ways (nuubui-home 66, Quick Menu 50, labwc 16 MiB: they get huge pages even under madvise, i.e. they ask for them), MemAvailable 590-606 MiB both ways: madvise changes nothing measurable. (5) Hardware watchdog (user request 2026-10-14): `S12nuubos-watchdog` runs BusyBox `watchdog -F -t 4 -T 16 /dev/watchdog` under `chrt -f 50` (`sunxi_wdt` module, 16 s = the sunxi maximum); `nuubos-suspend` stops it before the sleep (magic close, `sunxi_wdt` has no suspend handling and would reset a sleeping console) and starts it again on both exits. Verified: SCHED_FIFO, a 30 s deep sleep (RTC wake) without reset, `kill -9` of the daemon (no magic close) reset the console after ~17 s and it came back with the watchdog running; a hang of the whole SoC now restarts the console (and spends a try of a new A/B slot) instead of needing a forced power-off. Not done: trimming the arm64 defconfig drivers (1919 built-in options; keep SCSI for usb-storage and COMPAT for the armhf Steam Link).
- No persistent kernel log (2026-10-14): a 1 MiB ramoops region (DT `reserved-memory` at 0x5e000000, `PSTORE_RAM=y`, console/pmsg) registered fine, but after any reset (watchdog reset from PSCI `SYSTEM_RESET`, panic or plain `reboot`) the whole region reads zero (a temporary print of the raw headers at probe: sig/start/size/data all 0, ECC clean, so cleared, not decayed). U-Boot/SPL write nothing there (the boot0-style validator touches only the DRAM base, base+size/2 and base+size/4, ≤ 32 KiB each) and the AXP717 does not power-cycle (REG 20 = 0 after a software reboot): the DRAM content is lost in the SPL's DRAM re-init (LPDDR4 reset/re-training without self-refresh). ramoops would need the DRAM kept in self-refresh across the reset and an SPL resume path (same work as deep sleep stage 3 below); reverted, `PSTORE_RAM` stays a module with no region. Netconsole cannot help either (mac80211 has no netpoll).

## Kernel, display and suspend notes (§37.4)
- Kernel-stage limitation: with HDMI connected at boot the DRM fbdev is created at the mode common to panel and HDMI (640x480), so the kernel boot/poweroff splash appears small on HDMI. Fixing it needs a KMS-based splash path (platform work).
- Boot-with-HDMI → unplug → black panel (`sun50i-iommu ... Page fault (master 0, dir rd)` on each CRTC switch): root cause is `commit_tail_rpm` (ACTIVE_ONLY) skipping planes disabled together with their CRTC, so sun8i layers kept a freed/unmapped IOVA enabled and the DE faulted on the next CRTC enable. Fix: kernel patch `0026-drm-sun4i-disable-layers-with-their-crtc.patch` (2026-10-05).
- Boot-with-HDMI → panel black for the whole boot (backlight on, every SoC register identical to a good boot; even the TCON colour-bar test pattern stayed black): TCON LCD0 and TCON TV0 share `pll-video0`; all CRTCs are mode set before any is enabled and the TCON took rate exclusivity only at enable, so the HDMI mode set retuned the PLL and the panel was initialised at 99 MHz instead of 27 MHz. Fix: `0027-drm-sun4i-tcon-lock-dclk-rate-at-mode-set.patch` (rate exclusive from mode set; HDMI then moves to `pll-video1`). Hardware-confirmed 2026-10-05. Boot-without-HDMI → plug → unplug always worked because the panel already held the PLL.
- Sleep → spontaneous wake after ~1 min (seen as "Wi-Fi lost" toast + screen back on): the AXP717 IRQ line is wake-armed (power key shares it), so the `GAUGE_NEW_SOC` IRQ added by patch 0100 ended s2idle on every 1% SOC step. Fix: `0101-power-supply-axp717-mask-soc-irq-during-suspend.patch` (SOC IRQ disabled in suspend, one `power_supply_changed` on resume). To find a wake source: diff `/proc/interrupts` across the sleep and read `/sys/class/wakeup/*/last_change_ms`. Wi-Fi deauth during suspend (`DEAUTH_LEAVING`) is normal: rtw88 has no WoWLAN.
- Short black flash on every composition→direct-scan-out switch: DE33 mixer commit writes no `SUN8I_MIXER_GLOBAL_DBUFF`, so layer attributes and address do not latch together; fixed for the bottom layer by `0028-drm-sun4i-ignore-pixel-alpha-on-bottom-layer.patch` (2026-10-06, see §37.12). Any other per-frame attribute change on upper layers can still tear for one frame.
- Display clock check: `/sys/kernel/debug/clk/clk_summary` (pll-video0/tcon-lcd0/tcon-data-clock must read 81/81/27 MHz on the RG40XX-V panel).
- Display register debugging: `/sys/kernel/debug/regmap/{6511000,6515000}.lcd-controller/registers` and `*.mixer-top` are safe to read. NEVER read `1100000.planes-planes` or `*.mixer-mixer` regmaps: the read segfaults or hangs the whole SoC (target unreachable, needs a power cycle). Leave `drm.debug` at 0 on target; a high level during a modeset also locked it up. - Deep sleep (2026-10-11, user request; was planned after the RC): H616/H700 have no AR100/ARISC management core, so upstream TF-A forces `SUNXI_PSCI_USE_SCPI=0` (no crust for H616, U-Boot builds with `SCP=/dev/null`) and had no PSCI `SYSTEM_SUSPEND`: only s2idle. `patches/packages/arm-trusted-firmware/v2.15.0/0003-allwinner-h616-add-native-system-suspend.patch` implements it natively. CPU 0 stays powered (nothing else could power it back on). `pwr_domain_pwr_down` (C, from DRAM): CPU 0 to OSC24M, PLL_CPUX off, VDD-CPU (AXP717 DCDC1, reg 0x83) to 0.81 V over R_I2C (TF-A's mentor driver; R_PIO PL0/PL1 setup and the R_TWI gate/reset `R_PRCM+0x19c` are saved and restored around each access, Linux's mv64xxx re-initialises the controller on runtime resume), then copies `sunxi_standby_sram` (`plat/allwinner/sun50i_h616/sunxi_suspend.S`, position independent, no stack, caller-saved registers only, saved values at SRAM A1 + 0x7000) to SRAM A1 0x20000 (Linux does not use it; SRAM C belongs to the DE), turns the MMU off (BL31 and its tables are in DRAM) and runs it: MAER0-2 = 0, software self-refresh (`PWRCTL` bit 5, wait `STATR`=3; sequence from crust's H6 driver, BSD-3), PSI/AHB3/APB1/APB2 to OSC24M undivided, PLL PERI0/PERI1/GPU/VIDEO0-2/VE/DE/AUDIO off, WFI with `SCR_EL3.IRQ|FIQ` (GIC CPU interface left on; Linux's GIC masks non-wake IRQs on suspend), then the reverse (PLL lock waits, 20 us settle); MMU back on, VDD-CPU restored (+2 ms ramp), PLL_CPUX relocked, jump to `bl31_warm_entrypoint` (A53 cannot abandon a PSCI power-down). Stays on: VDD-SYS/GPU (DCDC2), VDD-DRAM, PLL_DDR and the DRAM controller clock, OSC24M (system counter, timekeeping). Tried and dropped 2026-10-11: clearing the DRAM controller `CLKEN` (and gating MBUS) in self-refresh: the controller never leaves self-refresh (`STATR` reads 0, breadcrumb `e6`, needs a forced power-off), so PLL_DDR off was not attempted (U-Boot also re-enables it with a vendor bit-30 toggle sequence). R domain (R_AHB/APB, R_I2C), the LED PWM counter (`PCCR23` source OSC24M) and the PIO debounce (LOSC) do not depend on PLL_PERI0. DCDCs are already in auto PWM/PFM (`0x81`=0). VDD-SYS stays on: devices and wake sources are as in s2idle. Before it, `PWRCTL`=0 at runtime: in s2idle the DRAM was never in self-refresh. Breadcrumbs (survive a forced power-off): RTC GP6 `0x07000118` = `0x5a5a000N`, last step reached (1 entry, 2 self-refresh, 3 PLLs off, 4 woken, 5 clocks back, 6 DRAM back; `0x5a5a00e1` self-refresh entry timeout, the suspend then returns at once; `0x5a5a00e6` self-refresh exit timeout, GP5 then holds `STATR`); GP5 `0x07000114` = `0x5a5b00NN`, DCDC1 register read before lowering VDD-CPU (`0x5a5bFFxx` = error code, VDD-CPU untouched). `/sys/power/mem_sleep` now reads `s2idle [deep]`; `nuubos-suspend` writes `mem` when `deep` is listed, `freeze` otherwise. Not done yet: drain measurement vs s2idle (`echo s2idle > /sys/power/mem_sleep` for the comparison), RG40XX-V/RG35XX Pro qualification.
- Deep sleep stage 3, DRAM controller/PHY/PLL_DDR off (work in progress, paused 2026-10-11 on user request; NOT in the patches, sources in the gitignored `local/wip-deep-sleep-dram-off/`, the CubeXX runs stage 2 again). How the stock firmware does it (vendor sun50iw9 BL31 = `monitor.fex` of the stock boot_package, no SCP; disassembled for the register sequence only, nothing copied): it saves 160 words at the DRAM base and at base+size/2 (PHY training patterns land there), enters self-refresh (`PWRCTL|=0x21`), clears RTC `0x1f4` bit0 (DRAM pad hold), DFI handshake (`SWCTL=0`, `DFIMISC` bit0 clear, `|=0x1f00`, `|=0x20`, `SWCTL=1`, wait `DFISTAT` bit0 = 0), then `CLKEN=0`, PLL_DDR0 off, DRAM_CLK bit30, DRAM_BGR gate/reset, MBUS gate/reset. On wake it re-runs its complete DRAM init (`INIT0` skip-init `0b01`, controller started in self-refresh, DFI init, pad hold released, self-refresh exit, MR writes, training) and restores the 160 words; same flow as boot0, which our U-Boot vendor backend mirrors. WIP design: U-Boot SPL publishes a handoff at SRAM `0x57f00` (`h700_dram_resume()` = `mctl_core_init()` with the boot's final para/config, resume mode releases the pad hold right before self-refresh exit like the vendor BL31); BL31 snapshots the SPL image at cold boot and, in suspend, maps SRAM C to the CPU (`syscon 0x03000004` bit24 = 1; Linux gives it to the DE), copies SPL back, saves 4+4 KiB, powers the DRAM side down and calls the SPL entry on a SRAM stack with a zeroed gd (its `get_ticks()` writes gd). Status: init, PHY training (`phy_ok`=1) and self-refresh exit succeed, `STATR`=1 even after `MAER`; the final `SWCTL=1` never gets `SWSTAT`, and at the 1 s timeout DRAM_BGR/DRAM_CLK read 0 and MBUS 0x01000002, i.e. the power-down sequence has been applied again after `SWCTL=1` (to investigate: a second pass through our standby/sys-init path, or a retry inside the SPL code). Each failure panics the SPL (watchdog reset). Debug aids: RTC GP0-GP5 (GP0-GP3 hold only stale stock-firmware values), `local/wip-deep-sleep-dram-off/mmio_trace.py` (annotates MMIO in an objdump listing).

## USB-C charging and AXP717 registers (2026-10-11)
- Some USB-C chargers do not charge with a C-to-C cable (USB `online`=0, no VBUS) while USB-A→C cables and PC ports always work. Hardware: the board presents no Type-C sink Rd, so spec-compliant sources keep VBUS off; "permissive" chargers give 5 V anyway. The AXP717 Type-C block is disabled by eFuse (`0x0B` bit 3 = 0, `0xE3` = 0x00); enabling it live (`0x0B`=0x1D, `0xE3`=0x11 SINK) left `0xE7` in DISABLE and a failing charger still did not charge (A/B tested on RG40XX-V): no software fix. No USB PD either (no PD controller, 5 V charger only). Workaround for users: USB-A→C cable or a C→A adapter.
- Power-on source: `0x20` = 0x04 after a VBUS-insert boot, 0x01 after a power-key boot (datasheet REG 20).
- Charging on/off: writing `Not charging`/`Charging` to `axp20x-battery/status` clears/sets `0x19` bit 1 (mainline driver; the current reads ~0 net, raw ~400 mA offset). CV limit `0x64`: 0=4.0 V, 1=4.1 V, 2=4.2 V. AXP717 never reports `Full`: the PMIC standby state maps to `Not charging`.
- PMIC registers: `/sys/kernel/debug/regmap/0-0034/registers` (cached) or `i2cget -f -y 0 0x34 <reg>` (live).

## Charge limit and charge screen (user request 2026-10-11)
- AXP717 battery current (2026-10-22): `current_now` (IIO `batt_chrg_i`, regs 0xCA/0xCB) is the charge-current ADC only; on battery it reads a constant ~368 whatever the load (CubeXX: 367-368 idle, 370-371 with 4 busy cores), and the PMIC has no discharge-current ADC (0xC4 VBAT, 0xC6 VBUS, 0xC8 VSYS). So nothing on the device can measure discharge or sleep current; the Performance overlay's `battery.power_mw` (V x current_now) is meaningless while discharging. Sleep drain must be measured from outside (USB meter with charging held by the charge limit below the current SOC: the system then runs from VBUS) or from the SOC drop over hours.
- Charge limit: kernel `0102-power-supply-axp717-charge-limit.patch` adds the standard `charge_control_end_threshold` (50..100, default 100 at every probe, which also re-enables charging) to the AXP717 battery. The driver applies it on every `GAUGE_NEW_SOC` IRQ and on every write: charging stops at the limit (`0x19` bit 1) and resumes 5 points below it. `status` reads `Full` while the limit holds charging, or in PMIC standby on VBUS at 100 % (before this patch the AXP717 never reported Full). In s2idle the SOC IRQ is masked (0101), and at power off nothing watches the gauge, so the driver then lowers the CV to 4.1 V when the limit is ≤90 % and charging is not held (approximately 90 %; restored on resume, and by the DT `voltage-max-design` at probe). A limit already held stays held at power off. To verify on hardware: what the gauge reads after a charge that ended at the 4.1 V cap.
- Setting: nuubos-systemd `CHARGE_LIMIT` (80..100 in steps of 5, default 100), `SET CHARGE_LIMIT n`, STATUS `charge_limit=` + `charge_limit.supported=` (whether the attribute exists). Applied when systemd starts and on SET. UI: Settings → Power row 5 and the web Power page (`system.chargelimit`).
- Charge screen: `nuubos-charge` (nuubos-splash package) runs from `S08nuubos-charge`, which blocks rcS. It shows the screen only when REG 20 has VBUS (0x04) and not the key (0x01); a software reboot reads 0. A battery must be present and the charger online, otherwise boot continues. Not with an HDMI display connected (user decision 2026-10-16: a docked console boots; the screen is drawn on the panel only, so on an RG35XX Pro with panel and battery unplugged the TV stayed black until Power was pressed). Battery `present` is the AXP717 REG 00 bit 3 and read 1 with the battery unplugged on that Pro: a better presence test needs the values measured without a battery (`S01nuubos-bootlog` now writes `13-power.txt`: every power_supply uevent and REG 00/01/04/20) — open. The screen shows the splash wordmark, with the track as the gauge (dimmed above the limit, limit label under its edge), the percentage and the voltage, and digits only, so nothing needs localizing. The gauge goes red→orange→green relative to the limit, the same on the RGB rings through rgbd FRAME (lightingd is not running yet). The program writes CHARGE_LIMIT to the kernel itself because systemd is not up.

U-Boot loads the uncompressed 21.7 MB `/boot/Image` at ~22 MB/s (a 20 MB longer Image: +0.9 s), ~1.0 s. A compressed kernel does not pay: U-Boot already has `kernel_comp_addr_r`/`kernel_comp_size` (sunxi-common.h), but LZ4 (frame format, 11.0 MB) booted in 7.89 s and gzip (9.3 MB) in 7.72 s: decompression and the move back cost what the shorter read saves. The kernel config is arm64-defconfig-shaped (ACPI, PCI, KVM, EFI, netfilter): a smaller Image would save ~0.045 s per MB. A resume restores it too, and without it resets into a cold boot (`0x5a5a00f4` in GP6) instead of waking with the profile's delays.
