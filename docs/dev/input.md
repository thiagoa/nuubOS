# Input / controllers

## Product rules (§26)
Controller-first with logical actions, never controller-brand semantics. Required before the relevant final milestone: Controller Mapping, Input Tester, RGB Lighting where supported. Mapping reset belongs to Reset System Settings. Default face roles (2026-10-07): `menu_confirm` = BTN_SOUTH (bottom), `menu_back` = BTN_EAST (right), in controllersd defaults, inputd defaults/`input-bindings.conf`, tester and labels. Games are unaffected: the game gamepad emits `menu_confirm`→BTN_SOUTH and `menu_back`→BTN_EAST, so physical east stays RetroArch A. Extra logical actions: `face_north` (Favorite on Home, home-users-oob.md), `face_west` (Game Details, emulation.md §37.18). Game gamepads/hotkeys: emulation.md §37.13. Physical keyboard: ui.md §37.24.

## Controller mapping (§37.3)
- Controller mapping (owner `nuubos-controllersd`, D-Bus `org.nuubOS.Controllers1`): 17 button controls + `left_x/left_y/right_x/right_y`; each bound to one source `key:CODE`, `abs:CODE:+|-` (half axis; on a stick axis = normal/inverted), `abs:CODE:>|<` (full trigger travel from min/max) or `none`. Defaults are derived from the device's evdev capabilities (D-pad keys or hat, L2/R2 keys/Z-RZ/BRAKE-GAS, right stick RX/RY or Z/RZ); `/state/users/<u>/controllers/<hex-id>.conf` stores only differences (legacy `action=305` still read). Capture: `BeginRemap` → inputd sends `RAWBASE`/`RAWREADY` baselines (normalized -100..100) → stick vs trigger is told apart by rest position; 5 s timeout (`RemapCancelled`), any button cancels a stick capture; a source already in use is swapped (same kind) or unassigned (other kind). inputd only consumes the navigation actions + `left_x/left_y` (stick navigation) and parses the same format. Input Tester `InputEvent` carries the resolved logical control and value (buttons 0..100, sticks -100..100).
- Input Tester UI (settings-view 14, user request 2026-10-08): `ControllerTesterVisual` in home.slint draws a brand-free pad on a 360x200 grid scaled by `u` (top-aligned, M3 Theme tokens; triggers fill with analog travel, stick knobs move with the logical value). Below it the last-input chip and the exit combo `H + START` (i18n 740): controllersd ends the tester when Hotkey and Start are held together (`TesterExitRequested`), because the tested controller's Back is captured. Navigate/Select hints are hidden on that page. Headless: ui-shot scene `tester`.

- Analog stick poll rate (battery audit 2026-10-14): nuubos-inputd writes `/sys/class/input/eventN/device/poll` of `adc-joystick` devices: 4 ms (the device-tree rate) while a game owns the controllers, 32 ms in menus (stick navigation; 16 ms until 2026-10-20: measured on the CubeXX idle Home 2145 context switches/s at 16 ms vs 1154 at 100 ms, the poller kworkers 406 → 73/s; in a game 4 vs 8 ms changed nothing measurable in CPU, so games keep 4 ms), 100 ms while `/run/nuubos/screen-off` exists (inotify on /run/nuubos); written only when it differs, logged as `stick poll eventN M ms`. - Rumble (user request 2026-10-18, "rumble must also work over Bluetooth"): the game gamepads (`nuubOS Gamepad`) declare `EV_FF`/`FF_RUMBLE` (`ff_effects_max` 16; uinput opened O_RDWR) and inputd serves the uinput FF protocol in its poll loop (`vpad_process`: `UI_FF_UPLOAD`/`UI_FF_ERASE` with BEGIN/END ioctls, `EV_FF` plays). An effect plays on every input of the same player that has `FF_RUMBLE` (inputs are opened O_RDWR): the controller's own evdev (kernel force feedback: xpad/hid-microsoft, hid-playstation, hid-nintendo...) and, for `builtin`, the `pwm-vibrator` device. Vibration Intensity (user decision 2026-10-27, GitHub #20; replaces the internal-only Internal Rumble switch): rumbled's per-user `RUMBLE=off|light|strong` in `/state/users/<id>/input-feedback.conf` (default light; a former `INTERNAL_RUMBLE=0` reads as off; D-Bus `GetMode`/`SetMode`, `GetState`/`SetEnabled` kept), re-read by inputd on change (`rumble_mode()`, a change drops the uploaded effects so they go up again filtered), for every controller: off plays nothing, light zeroes magnitudes below `RUMBLE_LIGHT_MIN` (0x3333, 20 %) and plays nothing when both are gone, strong plays everything. Why: Crazy Taxi (Flycast Puru Puru, faithful to the game) sends ~70 ms pulses at 1/7 every 0.1-0.5 s while driving (measured on the CubeXX 2026-10-27, pwm debugfs at 20 Hz), a constant buzz on the motors; hits come at 3/7-7/7. UI: Settings → Controllers & Input → Vibration Intensity (strings 1402-1406, dropdown, Test Rumble only with a built-in motor), web Controllers page (admind `rumble.mode`, `rumble` reports `mode`). Verified on the CubeXX with `tools/ff-test game` (wait for it to finish: it takes ~1.5 s to turn the gamepads on): light 1/7 -> 0, 3/7 -> 43 %; strong 1/7 -> 14 %; off -> 0. Effects are uploaded to a target at its first play and again after an update (`ff_gen`); a rescan reopens the inputs and drops them, so they are uploaded again at the next play. Nothing rumbles under the Quick Menu (plays forced to 0, playing effects stopped by `vpad_release`); gamepads off erases them. Covers RetroArch, Moonlight and Steam Link (Valve's app rumbles the SDL gamepad). Log: `rumble target player=N path=...`, `rumble upload failed`. Not yet: controllers whose kernel driver has no force feedback (8BitDo Ultimate 2C over Bluetooth = hid-generic, `B: EV=b`): needs the controller's own output report (hidraw) or a kernel driver.
- Restart gotchas (2026-10-18): `S47nuubos-inputd stop` now waits for the daemon to exit (a `start` right after found the exiting process in the pidfile and started nothing: `deploy-target.sh -s` left the console without inputd); `restart` (handoff) was already fine. controllersd ignores SIGPIPE: an inputd restart used to kill it (pad maps written to the closed socket), and without it inputd creates no game gamepads (Steam Link: "no controllers"). After restarting inputd by hand, check `pidof nuubos-controllersd` and the `padmaps updated` line.

- Terminal (2026-10-27): `TERMINAL ON` puts inputd in the Web Mode keyboard mode with the terminal key table (`term_keys`, `web_map`; no pointer); system.md "Terminal application".
- Stick deadzone (GitHub #19 "cardinal snapping", 2026-10-27): the per-controller deadzone (default 20 %) was applied per axis (`apply_deadzone`), which zeroed the small axis near the cardinal directions: the game gamepad's stick snapped to them (Zuma on PSP). Now `radial_deadzone()` per stick: a circle of that radius, the travel beyond it rescaled along the stick's own direction (capped at full deflection, so a square gate's corners are not beyond it); the raw values of both axes are kept per game gamepad (`vpad.raw`) and for Web/Terminal mode (`web_raw`). Host check: (32767, 3000) gave (32767, 0) before, now (32630, 2987). Home/Quick Menu navigation (`enter_delta`) unchanged. To check in a game with free aiming.
- Other programs' uinput devices are outputs, never inputs (2026-10-25): inputd skips a device whose sysfs node is under `/sys/devices/virtual/input/` unless its name starts with "nuubOS " (its own game gamepads/keyboards are skipped by name anyway; dev pads like `nuubOS bench pad` stay inputs; Bluetooth pads come through uhid, `/devices/virtual/misc/uhid`, and are not affected). Log `input-skip path=... (uinput output)`. Found with PortMaster: gptokeyb's "Fake Keyboard" (game gamepad -> keys for the port's Wayland window) was opened and EVIOCGRABbed by inputd during the session, so labwc and the port got no key at all (a second EVIOCGRAB answered EBUSY).

## Lost releases / "ghost input" (2026-10-21)
User + Reddit report (RG40XX V/V2, also in menus): "it starts moving by itself as if a button were held". Reproduced on the CubeXX with `tools/input-drop-test` (dev aid: a uinput pad presses D-pad Down, inputd reads it, then inputd is SIGSTOPped while ~1200 axis events and the release are written; `input-drop-test INPUTD_PID [settle_s] [ready_s] [unplug]`, wait ≥6 s after creating the pad: inputd reopens it once controllersd maps it and a reopen drops what was queued): the old inputd kept emitting `navigation-repeat action=menu_down` forever (Settings scrolled by itself), even after the pad was removed.
- Cause: inputd ignored `SYN_DROPPED`. When it falls behind, the kernel's per-client evdev buffer (small, ~64 events for the stick) overflows, the queued events are discarded and the release (or the stick's return to centre) is lost: the game gamepad keeps the button/axis held, the navigation repeat (inputd's own, stopped only by the matching release) keeps scrolling. The H700 adc-joystick is polled every 4 ms (DT `poll-interval`), so a moving stick fills that buffer in well under 100 ms of inputd delay.
- Fix: per input `keys` (last seen EV_KEY state, initialised with EVIOCGKEY at open) and `dropping`: from `SYN_DROPPED` to the next `SYN_REPORT` events are discarded, then `resync_input()` reads EVIOCGKEY/EVIOCGABS and replays the differences (keys) and every axis value through the same `process_events()` path (game gamepads, hotkeys, navigation). Log `input-dropped` / `input-resync replayed=N`. Safety net: `navigation_repeat_tick()` stops a repeat whose action is no longer held on any input (live EVIOCGKEY of the bound key, abs binding state, nav-axis direction) and broadcasts the missing release (`navigation-repeat stop ... reason=not-held`).
- Verified on the CubeXX with the tool: drop → resync replayed the release, no repeat. Removing a pad while a key is held already produced the release (the kernel releases keys on unregister). Not yet seen on the user's RG40XX V/V2 after the fix (needs play time); in-game path covered by the same replay, not separately measured.
- D-pad direction "stops responding, recovers after a while" (Reddit, RG SP, 1.0.0-rc.1, 2026-10-21; the reporter's setup not known: whether Bluetooth devices were connected). Mechanism that fits: the game gamepad's D-pad is a hat (`vpad_set_button`: x = right - left), so a direction left held on the game gamepad cancels the opposite one until it is pressed and released again. Ways a held state can go wrong besides `SYN_DROPPED` (unlikely on an SP: no sticks, gpio-keys evdev buffer 64 events): (1) any `/dev/input` create/delete (Bluetooth controller or headset/AVRCP connecting or sleeping, a uinput device) makes inputd `rescan_inputs()` close and reopen every input: events in the gap are lost and the new `keys` baseline comes from EVIOCGKEY, so a release in the gap is not replayed to the game gamepad; (2) the same change makes controllersd push PADMAP twice, and `commit_padmaps()` calls `release_all_vpads()`: a direction held at that moment is dropped until it is pressed again; (3) while the Quick Menu button is held every event is consumed, so a direction pressed during a chord and still held afterwards does not reach the game. Fix (2026-10-21): (1) `rescan_inputs()` keeps every input still there open with its state (`input_still_there`: same path, EVIOCGNAME answers with the same name, same `st_rdev`), opens only new nodes and closes only vanished ones (log `input-close`); (2) `commit_padmaps()` compares the new table with the current one (`changed=0|1` in the log; controllersd sends it 2-6 times per device change) and only on a real change releases the game gamepads and then replays what the players still hold through the new mapping (`replay_held_controls`: `keys` + EVIOCGABS through `forward_game_event`; not under the Quick Menu, the hotkey modifier or Web Mode). Case (3) left as is: replaying there would press a chord's button in the game. Reproduced and verified on the CubeXX with `tools/dpad-hold-test` (uinput pad holds Right in a running game, another device appears; `dpad-hold-test [ready_s] [pad]`, `pad` = the second device is a controller that gets a player): before, the nuubOS Gamepad's hat went 1 -> 0 while Right was still held; after, 1 stays 1 (remote and second controller), and a release made as a device appears still arrives (0).
- Menus scrolling by themselves again (user report 2026-10-22, CubeXX, built-in controls only, no Bluetooth; logs lost to a reboot): while a game owns the controllers and the Quick Menu is closed, stick/hat events go to the game only (`process_events`), so `process_nav_axis()` never sees them and `axis->direction` keeps its last value. A stick held in the Quick Menu over a game (repeat `menu_down` running) while the menu closes left `direction` = +1 after the stick returned to centre; the safety net trusted that cached direction, so the repeat ran forever: Home scrolled in the background during the game and the Quick Menu scrolled by itself when opened again (until the stick crossed the thresholds again). Also `navigation_action_held()` counted a failed `EVIOCGKEY` as held. Fix: (1) the safety net confirms a stick direction / abs binding with the live `EVIOCGABS` value (beyond the release threshold), and a device that cannot be read holds nothing; (2) `reset_pad_navigation()` forgets the pads' axis directions and abs-binding states and ends a running repeat with its release (log `navigation-repeat stop ... reason=owner-change`) whenever the controllers change hands: Quick Menu opened/closed while a game runs, game gamepads or Web Mode on/off; (3) the repeat never runs while a game owns the controllers with the Quick Menu closed (`reason=game`). Reproduced and verified with `tools/nav-owner-test` (dev aid: uinput pad with a stick, `GAMEPADS ON`, `MENU OPEN`, stick down, `MENU CLOSE` with the stick held, stick to centre; counts `menu_down` presses on a generic subscriber; needs emuctl idle; `nav-owner-test [ready_s]`): old inputd 17 presses in 1.5 s after the close and 16 after reopening (FAIL), new 0 / 0 (PASS). If it happens again: do not reboot, grab `/run/nuubos/inputd.log` first (it is on tmpfs). Again 2026-10-22 (CubeXX, after a resume, Quick Menu open): `menu_left` repeated from the left stick (`adc-joystick` X 761 for ~14 repeats, then back to 2067; just before Y went to 4035 and back), the D-pad keys after it were the user's; whether the stick was touched is unknown. Possible causes to check: the sun20i GPADC has no suspend/resume callbacks and keeps `last_channel` across a resume, the two axes share one ADC channel through `adc-mux`. inputd log lines carry monotonic seconds since then (`[  8329.554]`, same clock as dmesg) to put such events next to `PM: suspend exit`; that log copy is `/userdata/inputd-ghost-20261022.log` on the CubeXX.
- Input latency measured (2026-10-23, CubeXX, panel 60 Hz, tools in the session scratchpad, not in the repo): a press written into the built-in pad's evdev node (`gpio-keys-gamepad`, BTN_SOUTH; inputd is not exclusive, so it sees it as real), a probe libretro core (white while a button is held, logs when retro_run sees it and when it calls video_cb; bind-mounted over a core for the test) and an LD_PRELOAD shim (eglSwapBuffers enter/return and wl_display_flush in RetroArch through a wrapper bind-mounted over /usr/bin/retroarch, because emud starts it with a clean environment; drmModeAtomicCommit and the page-flip handler in labwc through `LD_PRELOAD=... S50nuubos-ui start`). No ftrace in the kernel. Chain, ms from the press (mean of 40, random phase): inputd -> virtual pad 0.16; core sees it 8 (half a frame: RetroArch polls ~0.5 ms after each vblank); before Mesa 0007 the frame was committed only at the END of the next swap (Mesa waits for the previous frame callback, then attaches), just after labwc had composed at vblank + 0.27 ms, so it waited a refresh in the swap and a refresh in labwc: 57 ms to the vblank that shows it. Mesa 0007 (`NUUBOS_SWAP_WAIT_AFTER=1`: commit at once, then wait for that frame's callback; same frame rate) -> 40.6 ms. Plus the 5 ms debounce and the panel scan-out. emud sets it for every system except `heavy_system()` (Dreamcast/NAOMI/Atomiswave, N64, PSP, NDS, Saturn): Crazy Taxi while driving fell from ~60 to 40 fps with it (user), frames reach the GPU late and, committed at once, miss the vblank. RetroArch frame delay on the probe core: 8 ms -> 34.9, 12 ms -> 29.5 ms (light systems only: the core then has 16.7 - D ms). The remaining refresh is labwc composing right after the vblank (a late "render deadline" in labwc would remove it). Shipped 2026-10-23 (emud `write_session_cfg`): light systems get `video_frame_delay = 0` + `video_frame_delay_auto = true` (RetroArch 1.22: target 3/4 of a frame, 12 ms; it lowers the delay itself when the core's run time no longer fits), heavy systems auto off. Probe: 29.8 ms (n=40). Pacing with real games (swap returns, 40 presses each): NES, SNES (Aero Fighters), GBA, PC Engine 60.00 fps, 0 intervals > 20 ms; PAL Mega Drive / PlayStation at their 50 Hz cadence as without the delay; PICO-8 (FAKE-08) 1 missed frame with and without the delay, but the swap-return jitter (18-28 ms intervals, labwc composing on commit while idle) 172 -> 328 of ~1300: not on screen (59.95 fps both). Measuring tools: the shim must stay out of nuubUI (it segfaults with it preloaded; three crashes put the console in safe mode twice on 2026-10-23): the shim drops LD_PRELOAD in labwc and RetroArch.
- Input latency notes (audit 2026-10-21, not measured end to end): every gpio-keys button has the kernel default `debounce-interval` 5 ms (no DT sets it; sunxi pinctrl has no per-pin debounce, so gpio_keys uses its hrtimer: each press and release reaches evdev 5 ms after the last edge); since kernel 0111 the first edge is reported at once, see "Ghost D-pad from the kernel"). RetroArch: `video_frame_delay` 0, run-ahead/preemptive frames off, no threaded video except NDS; the Dreamcast core's threaded rendering adds one frame by design (emulation.md).

## Ghost D-pad from the kernel: gpio-keys debounce (2026-10-24, kernel patch 0111)
User report (RG SP, latest main with every inputd fix): in Darius R (GBA) a released D-pad direction stays held, frequently, every direction; pressing it again releases it. Proven on the CubeXX with `keywatch` (dev aid in the session scratchpad: every 1 ms compares EVIOCGKEY of `gpio-keys-gamepad` with the PIO data register read through /dev/mem, PA at 0x0300b010, PE at 0x0300b0a0, active low; prints mismatches > 20 ms): in a few minutes of play 3 cases, Up 653 ms and 388 ms, Right 279 ms, all `kernel=1 pin=0`, each ended only by the next press. So the kernel itself held the key: inputd and its EVIOCGKEY safety net see the same wrong state.
- Cause: gpio_keys (no DT `debounce-interval`: 5 ms software debounce on an hrtimer) reads the pin ONCE when the timer expires, 5 ms after the last edge interrupt. The H616/H700 PIO detects edges (double-edge mode 4) on the pins sampled by its debounce clock, LOSC 32 kHz with prescaler 0 (`IRQ_DEBOUNCE` registers 0x0300b218/298 = 0), while the data register reads the pin directly: bounce shorter than ~31 us changes what the read sees without raising an edge. A read that catches such a spike reports the wrong level and no later edge corrects it.
- Fix, patch `0111-input-gpio-keys-eager-debounce-with-verification` (EV_KEY buttons on a GPIO readable in IRQ context, i.e. every H700 gamepad/volume key): the first edge reports the level read at once (press and release no longer wait 5 ms), later edges restart the quiet interval, its end reports the level only when 3 reads 20 us apart agree (else 1 ms later), and the level is read every 10 ms while a key is reported pressed and 3 times after a release: two disagreeing reads in a row correct it (kernel log `missed edge, level N`, ratelimited). Cost: a 100 Hz timer per held button (10 ms, was 20 in the first test: corrected in 39 ms).
- Verified 2026-10-24 on the CubeXX (user playing, `keywatch` running): with 0111 (20 ms check) one release missed by the edge detector (button A, `kernel=1 pin=0`) was corrected after 39 ms with `missed edge, level 0` in the kernel log, without a new press; the check is now 10 ms. Before 0111 the same few minutes gave 3 stuck directions of 279-653 ms. Backups on the CubeXX: `/userdata/Image.before-0111`, `/userdata/keywatch-before-0111.log`.
- inputd scheduling (2026-10-24): `SCHED_FIFO` priority 10 (`SCHED_RESET_ON_FORK`). Measured with `latprobe` (dev aid in the session scratchpad: writes a key into `gpio-keys-gamepad`, times its arrival on the player-1 `nuubOS Gamepad` with CLOCK_MONOTONIC evdev timestamps, 300 presses/releases at random phase) under Virtua Fighter 2 on the CubeXX: SCHED_OTHER mean 0.49 / p99 3.1 / max 5.0 ms, SCHED_FIFO 10 mean 0.30 / p99 0.79 / max 1.36 ms. `process_events()` now flushes the game gamepads before the RAW stream to controllersd (socket writes the game need not wait for).

## UI confirm/back swap (2026-10-24, user request)
User report: nuubOS's own menus confirm on the South face button while RetroArch's own menu (unswapped default) confirms on East, so the two disagreed out of the box; the existing per-controller Controller Mapping screen could not fix only the UI side, since it is the same source `controllersd` sends as the game padmap (remapping `menu_confirm` there remaps a game's South/East too, confirmed by reading `push_padmaps()`/`load_mapping()`). Fix: `nuubos-inputd`'s existing `BIND SET/GET/RESET` protocol already operates on its own global `bindings` table (`/state/config/nuubos-input.conf`), entirely separate from `controllersd`'s per-controller mapping files and the padmap built from them — a game's own buttons are unaffected either way. Exposed as a Settings → Controllers & Input toggle ("Swap Confirm/Back Buttons", `controllers_menu_rows`/settings-view 10, row 2): confirm calls `BIND SET menu_confirm`/`menu_back` swapped; the hint icons update at once (`refresh_hint_mapping` already read `BIND GET` live). `nuubos-emud` reads the same `/state/config/nuubos-input.conf` file at every session launch (`ui_confirm_is_east()`) and sets RetroArch's `menu_swap_ok_cancel_buttons` to match — mind the polarity: RetroArch's own unswapped default already uses East as its menu OK, so nuubOS on East means `"false"` (RetroArch unchanged) and nuubOS on South means `"true"` (RetroArch swapped away from its own default); got this backwards once and had to flip it after a live test showed RetroArch's menu going the wrong way.
- Found and fixed along the way: `BIND SET`/`BIND RESET` only ever updated the global `bindings` table; each already-open input's own `mapped_codes` cache (what `action_for_code()` actually reads on every key event) was derived from it once, at open/rescan time, and never noticed a later change — a swap persisted correctly and the hint icons updated immediately through `BIND GET`, but physically pressing the new button did nothing until `nuubos-inputd` was restarted by hand. Fixed by having both commands re-run the same per-input setup a rescan would (`refresh_all_controller_mappings()`, calling `configure_input_mapping()` for every open input) before replying `OK`.
- Restart gotcha found during testing (2026-10-24, RG-SP): restarting `nuubos-inputd` while RetroArch is already running stops the *game's* controls (nuubOS's own in-game Quick Menu/Home still responds) — RetroArch opened the old `nuubOS Gamepad` uinput device at launch and does not notice a new one appearing after a restart recreates it. Restarting RetroArch itself (not just inputd) makes it redetect the device and recover. Not an issue for this feature specifically, since `BIND SET` alone (via the fix above) never requires restarting inputd at all; worth knowing for any future inputd restart during an active session.

- Per user (user decision 2026-10-25, merge of PR #1): inputd loads the active user's `/state/users/<id>/nuubos-input.conf` over the device's `/state/config/nuubos-input.conf`; `BIND SET` writes into the user's file only the bindings that differ from the device layers (so a later device change still reaches the user), the device file without an active user; `BIND RESET` (Reset System Settings) removes the device file only, the users' swap stays. A user switch (usersd renames `/run/nuubos/user/active`; inputd watches `/run/nuubos/user`, added when the folder appears) reloads the bindings and every open input's mapping. emud asks `BIND GET menu_confirm` instead of reading the files. Strings 1371/1372 (the PR's 1357/1358, taken by PortMaster); default stays South (nuubOS layout), never called a "Nintendo layout" in the UI.

## Bluetooth rumble: Xbox One S 1708 (2026-10-21)
User report: "Bluetooth rumble does not work" (Xbox Wireless Controller 045e:02fd, classic BT, firmware 9.03, BlueZ 5.86 with UHID). Diagnosis on the CubeXX with `tools/ff-test` (dev aid: `ff-test /dev/input/eventN|game|game2 [strong] [weak] [ms]`; `game`/`game2` turn inputd's game gamepads on like emud and play on player 1/2's nuubOS Gamepad): a raw report on `/dev/hidraw0` with enable 0x0f vibrated, the driver's report (enable 0x03, weak|strong only) is ignored by this firmware. Kernel patch 0018 (enable all four actuator bits for the 1708) had zero-context hunks written for the v0.5 kernel: on 7.3 its table hunk landed on the 8BitDo SN30 Pro+ entry, so the 1708 never got the quirk. Regenerated with context against 7.3 (the SN30 Pro+ back to upstream `MS_QUIRK_FF`); a scan of every kernel/package patch found no other zero-context hunk on an existing file (only libdisplay-info's one-line meson.build). Verified: player 1 (Xbox) through inputd rumbles and stops; player 2 (built-in) drives `pwm-vibrator`. Pitfalls: a direct EV_FF write to a controller is silently dropped while inputd grabs it (only the grabbing handle may inject); a hidraw report with loop count 0 rumbles forever (stop: `03 0f 00 00 00 00 00 00 00`).
